# 2026-08-12 阶段 11 发布后公网传输超时

## 影响

阶段 11 三次生产发布都在公网冒烟阶段失败，保护流程三次成功恢复上一版本。已验证版本持续可用，没有把未通过检查的新版本留在生产。

## 证据链

1. 三次发布都先完成本地测试、容器启动和服务器 `127.0.0.1` 健康检查。
2. 公网失败随机分布在首页、开始页、路线、试教、发现和作品页；新增 `/pilot/guide` 多次返回 200，因此不符合单一路由代码故障。
3. 错误同时包含 SSL 连接超时和响应体只传输一部分后超时。
4. DNS 始终解析到目标服务器，Let's Encrypt 证书域名和有效期正确。
5. 每次自动回滚后，强制直连目标 IP 的 10 次健康采样全部返回 200，但 TLS 握手仍有约 0.04–1.66 秒波动。
6. 第三次发布已经把 Docker 构建移到 GitHub Runner，但相同公网超时仍然复现，因此服务器现场构建不是充分根因。
7. 受保护 SSH 诊断显示主机 load 约 0.38、可用内存约 5.1GB、OpenVibe 容器约 42MB 且 0 次重启，本机健康请求稳定约 2ms。
8. 同一时刻，位于 East US 的 GitHub Runner 对 `/explore` 连续 5 次请求全部 SSL 超时或只传输部分响应体后超时。

## 根因判断

根因不是应用、容器或主机资源，而是 GitHub East US Runner 到亚洲服务器的跨区域公网路径持续不稳定。旧检查要求该单一远端完整下载多个大页面，把跨区域吞吐质量错误地当作应用发布健康，因而触发保护性回滚。

## 修复

- 服务器本机完整下载全部代表性页面并要求 2xx/3xx，验证应用和页面内容可完整传输。
- GitHub 公网只读取相同路由的响应头并要求 2xx/3xx，验证 DNS、TLS、反向代理和路由存在。
- 两层检查都对失败路由只做一次有界复核，持续失败仍回滚。
- 生产镜像改在 GitHub Runner 构建并压缩传输；服务器只加载镜像和启动容器。
- Compose 启动与回滚显式使用 `--no-build --pull never`，防止发布窗口重新触发构建或拉取。

## 防复发

- 保留每小时两次的可用性检查和独立重复延迟采样。
- 发布失败先保留回滚，不连续盲目重试。
- 保留只读诊断工作流；如本机完整页面也开始变慢，再评估共享服务器资源或迁移独立实例。
