# 2026-08-12 阶段 11 发布后公网传输超时

## 影响

阶段 11 两次生产发布都在公网冒烟阶段失败，保护流程两次成功恢复上一版本。已验证版本持续可用，没有把未通过检查的新版本留在生产。

## 证据链

1. 两次发布都先完成本地测试、容器启动和服务器 `127.0.0.1` 健康检查。
2. 公网失败随机分布在首页、开始页、路线、试教、发现和作品页；新增 `/pilot/guide` 多次返回 200，因此不符合单一路由代码故障。
3. 错误同时包含 SSL 连接超时和响应体只传输一部分后超时。
4. DNS 始终解析到目标服务器，Let's Encrypt 证书域名和有效期正确。
5. 每次自动回滚后，强制直连目标 IP 的 10 次健康采样全部返回 200，但 TLS 握手仍有约 0.04–1.66 秒波动。
6. 旧发布流程在共享服务器上执行完整 Docker 多阶段构建，随后立即切换并从公网建立多次独立 TLS 连接。

## 根因判断

应用代码故障的证据不足。最符合现有证据的根因链是：共享服务器现场执行依赖安装与镜像构建，放大了发布窗口的主机资源压力；公网 TLS 与响应传输发生持续抖动；一次性路由检查将抖动判为新版本故障并触发回滚。

## 修复

- 冒烟检查必须同时满足 HTTP 状态正常和完整传输成功。
- 第一轮失败路由只做一次有界复核，持续失败仍回滚。
- 生产镜像改在 GitHub Runner 构建并压缩传输；服务器只加载镜像和启动容器。
- Compose 启动与回滚显式使用 `--no-build --pull never`，防止发布窗口重新触发构建或拉取。

## 防复发

- 保留每小时两次的可用性检查和独立重复延迟采样。
- 发布失败先保留回滚，不连续盲目重试。
- 若移出构建后仍持续出现公网传输超时，再通过受保护的 SSH 通道一次性采集主机 load、内存、磁盘和容器资源证据，评估共享服务器邻居或迁移独立实例。
