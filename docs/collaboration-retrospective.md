# OpenVibe 人机协作开发总结报告

复盘周期：2026-08-09 至 2026-08-12  
项目地址：<https://github.com/qiuyiwu1989-star/openvibe>  
生产站点：<https://vibe.yongle.school>

## 一、结论摘要

OpenVibe 这次合作的成功，不只是“AI 在几天内写出了一个网站”，而是人和 AI 逐步形成了一套可以复用的产品开发机制：

> 人负责提出真实问题、判断方向和批准关键动作；AI 负责调查、拆解、并行执行和形成证据；契约、测试、审核门与生产验证负责防止双方过度自信。

从一句“把 GitHub 上有趣的项目抓起来，给刚学习 vibe coding 的人参考”，项目先完成开源项目雷达的纵向样板，再扩展为 30 个审核过的进阶案例；随后根据“项目太计算机、对新手太难”的真实反馈，把产品首入口调整为低门槛作品任务；又继续为 K12 场景发展出 20 个带分龄建议的案例、4 条四周路线、匿名试教工具和两套 90 分钟试教协议，最后完成 GitHub、服务器、HTTPS、自动发布、回滚、监控、发现和更新闭环。复盘时进一步明确：OpenVibe 的总定位是全年龄学习地图，K12 只是其中一条专项路径。

这次合作最重要的产物有两个：

1. 一个已经真实上线、可持续运行的产品。
2. 一套可以在后续 Vibe Coding 项目中复制的人机协作方法。

## 三、项目是怎样一步步长出来的

### 1. 先把想法压缩为产品命题

一开始没有直接堆页面，而是先明确 OpenVibe 不是另一个 GitHub Trending。它要回答的是：

- 这个项目是否值得学习？
- 它适合谁？
- 应该从哪里开始复刻？

同时写清楚“不做什么”：不自动发布、不执行第三方仓库代码、不急于建设登录、社区、排行榜和数据库。这些边界让后续 Agent 可以快速行动而不不断扩大范围。

### 2. 用 5 个项目打通纵向样板，再扩展到 30 个

阶段 1 没有一开始就追求“大而全”，而是用 5 个项目贯通：

```text
GitHub → 仓库事实快照 → 中文策展判断 → 人工审核 → 静态发布 → 项目详情页
```

只有抓取、策展、页面和 QA 四条链路全部跑通后，才把内容扩展到 30 个项目。这个顺序显著降低了返工：先验证结构，再扩大数据量。

### 3. 接受用户反馈，主动重写产品入口

项目第一次形成后，用户直接指出：“这些项目有点太难了，太计算机了，需要一些新手入门的。”这不是小修文案，而是对产品假设的纠偏。

团队没有继续维护原来的“技术项目目录”惯性，而是把产品改为两层：

- 新手层：15 分钟看到变化、2 小时完成一个可署名作品。
- 进阶层：再进入 30 个成熟开源项目的结构化学习路径。

这是本次协作中非常关键的成功经验：代码完成度没有凌驾于用户判断之上，已经完成的方案也允许被重新定义。

### 4. 从“案例网站”发展为全年龄创造者学习产品

后续先以 K12 作为学习设计试验场，没有只按年龄给内容贴标签，而是逐步加入：

- 问题、知识、工具、作品、反馈、身份六个学习环节。
- 学习者必须亲自承担的判断，以及 AI 可以帮助的部分。
- 4 个年龄入口与 4 条四周作品路线。
- 教师/家长引导卡、隐私边界和成人支持。
- 本机匿名试教反馈与可打印执行协议。

产品因此从“看别人做了什么”，走向“我能不能做出自己的作品，并解释自己的决定”。这套作者身份逻辑适用于所有年龄；K12 额外需要分龄表达、成人支持和未成年人安全，但不是产品总边界。

### 5. 功能达到验证条件后，主动停止无证据的 K12 扩张

阶段 11 明确冻结没有证据的 K12 扩张：不再继续加分龄案例，而是要求先完成两场真实试教。这个决定很重要，因为 Vibe Coding 最容易出现的偏差就是持续添加功能，用开发速度掩盖核心命题尚未验证。它限制的是 K12 专项扩张，不是把 OpenVibe 定义为 K12 产品。

## 四、为什么这次合作比较顺利

### 经验一：人做方向判断，AI 做高密度执行

用户的核心贡献不是逐行指导代码，而是在关键节点做价值判断：批准方案、选择阶段、指出内容太难、要求加入 K12、确认产品名称和生产域名。AI 则把这些短指令展开为产品结构、数据契约、页面、测试、部署和文档。

这种分工降低了沟通成本：用户不需要先成为技术经理，AI 也没有获得不受约束的产品决策权。

### 经验二：用短选项完成阶段授权

合作中多次使用“A”完成方案选择和阶段批准。它之所以有效，是因为每个选项背后已经给出清楚的目标、边界和影响。短回复并不代表含糊授权，而是建立在前置方案充分的基础上。

可复用做法是：

1. AI 先把复杂问题压缩为 2–3 个互斥方案。
2. 明确推荐项及理由。
3. 用户用一个字母快速批准。
4. 授权只覆盖当前阶段，部署、外部发布和生产写入另行确认。

### 经验三：先定义契约，再让多个 Agent 并行

项目先定义公共 Schema、数据对象和目录所有权，再把抓取、策展、Web、QA 分给不同 Agent。主 Agent 独占公共 Schema、根配置和最终集成，子 Agent 只修改授权目录。

这避免了常见的并行开发冲突：多个 Agent 同时改同一份核心文件、各自发明重复类型，或把临时结构直接当成公共接口。即使真实 GitHub 响应暴露了 304 身份字段等契约缺口，也由主 Agent统一调整，而不是各模块自行绕过。

### 经验四：把事实、判断和发布权分开

OpenVibe 没有把 GitHub 数据、AI 评价和公网发布混在一个对象里，而是拆成：

- `RepositorySnapshot`：仓库可核实事实。
- `EditorialProfile`：中文策展与学习判断。
- `PublicationRecord`：谁在何时批准发布。

自动化最高只能产生 `review`，不能直接变为 `published`。同样，持续发现和更新只上传待审 artifact，不自动提交和发布。这让 AI 可以高效处理大量候选，同时保留人对内容质量、许可证和风险的最终责任。

### 经验五：用测试和证据定义“完成”

每个阶段不是以“代码已经写了”结束，而是用类型检查、运行时 Schema、数据完整性、生产构建、桌面与移动端浏览器检查、服务器本机检查和公网检查形成证据链。

测试在这里不仅是防 Bug 工具，也是 Agent 之间的沟通协议。一个 Agent 不需要完全理解另一个 Agent 的全部上下文，只要公共契约和验收持续通过，就能安全接班和集成。

### 经验六：把失败变成架构升级，而不是反复重试

生产上线经历了两类真实问题：

1. 同机端口冲突、HTTPS 命中错误证书、远程构建期间 SSH 连接中断。
2. GitHub East US Runner 到亚洲服务器的跨区域 TLS 与大页面传输不稳定。

团队没有通过关闭证书校验、放松全部检查或连续盲目重试来“让发布变绿”，而是先取证，再分层修复：

- 使用独立端口、独立 Nginx 站点和匹配域名的证书。
- SSH 增加保活。
- 镜像在 GitHub Runner 构建，服务器只加载不可变镜像。
- 服务器本机完整读取页面，公网只验证 DNS、TLS、代理和路由响应。
- 延迟趋势独立监控，不因一次跨区域变慢就回滚。

三次失败发布都成功自动恢复旧版本，第四次在根因修复后上线。这里真正的成功不是“没有事故”，而是事故没有破坏生产，并最终沉淀为可复用的部署架构和事故文档。

### 经验七：安全边界没有因为追求速度而消失

合作期间涉及 GitHub、服务器和云服务，但最终仓库没有保存用户曾在对话中提供的密码、个人令牌或云密钥。生产改用专用 SSH 密钥和受保护的 GitHub Environment，密钥只在单次 Runner 中短暂落盘并及时删除。

另一个重要边界是：本地开发、GitHub 推送、生产部署分别授权。AI 没有把“帮我改代码”解释成默认获得公网发布权。

### 经验八：持续写阶段报告，让新会话可以接班

产品范围、架构决策、数据契约、Agent 契约、阶段报告、部署手册和事故记录都写入仓库。这样，对话不再是唯一的项目记忆；任何新 Agent 都可以从文件恢复目标、边界、现状和下一步。

这也是本次高速度没有完全演变为失控的根本原因：意图、状态、决策和验证被持续外化。

## 五、这次合作中仍可改进的地方

### 1. 目标用户验证发生得稍晚

早期 30 个项目更接近技术从业者的学习偏好，直到用户明确指出“太计算机”，产品才完成新手层重构。下次可以在正式扩容前，先用 3–5 个首页卡片或纸面原型向真实初学者验证“看得懂、愿意点、能开始”。

### 2. 开发速度一度快于真实学习证据

K12 内容、学习路线和反馈工具已经比较完整，但目前仍没有两场标准试教的数据。因此不能把“页面完整”“测试通过”直接等同于“学习设计有效”。阶段 11 设置停止线是正确纠偏，接下来应严格执行。

### 3. 项目状态入口还可以进一步收敛

项目已经有完整阶段报告和架构决策，但当前状态散布在 README 与多个阶段文件中。未来可以增加一份很短的 `TASKS.md` 或“当前状态页”，只保留 Now、Next、Blocked 和最近完成项，让跨会话接班更快。

### 4. 自动发现已经运行，但人工审核能力尚未形成节奏

首次发现有 55 条待审候选，更新扫描有 30 条待审记录。系统已经能持续生产队列，但如果没有固定审核人、审核频率和每次处理上限，artifact 会逐渐堆积。下一阶段需要把“每周发现”变成“每周处理多少、谁负责、哪些风险先看”的运营节奏。

### 5. 生产网络仍存在区域性延迟波动

当前应用和主机健康，跨区域公网链路仍偶尔变慢。现有分层检查已经避免误回滚，但这并不等于网络问题消失。应继续观察延迟趋势；只有真实用户体验数据表明影响明显时，再评估 CDN、边缘缓存或迁移服务器，避免过早增加基础设施。

## 六、可以复制到下一个项目的协作方法

可以把本次经验压缩为“六道门”：

### 第一道：命题门

- 一句话写清为谁解决什么问题。
- 写出 3–5 个明确不做事项。
- 确定这是原型、产品还是生产项目。

### 第二道：样板门

- 只选最小数量的真实对象打通端到端链路。
- 不在链路未闭合前扩大数量。
- 用真实数据暴露契约缺口，但不执行不受信任代码。

### 第三道：契约门

- 先定义 Schema、失败状态和目录所有权。
- 公共接口只由集成负责人修改。
- 多 Agent 按可独立验收的工作包并行，而不是按模糊职位并行。

### 第四道：审核门

- 自动化负责发现和建议，人负责批准。
- 事实、评价、发布状态分离。
- 外部发布、生产写入和高风险变更单独授权。

### 第五道：验证门

- 类型、Schema、测试、构建、浏览器、生产健康逐层验收。
- “完成”必须对应可重复运行的命令或可核实的页面。
- 失败先保留证据和旧版本，再处理根因。

### 第六道：现实门

- 软件验收后，必须回到真实用户和真实场景。
- 用小样本验证核心命题，不急于建设账号、增长和复杂后台。
- 下一阶段只由证据启动，不由“还能做什么功能”启动。

## 七、推荐的人机协作标准动作

每个新阶段都可以沿用下面的节奏：

1. **用户给方向**：说明想解决的问题或指出不满意之处。
2. **AI 做简报**：复述目标、用户、范围、不做事项和验收标准。
3. **用户做选择**：用 A/B/C 或一句话批准，不承担技术拆解负担。
4. **AI 写契约**：先固定数据、接口、所有权和失败方式。
5. **Agent 分工执行**：每个工作包有独占目录、交付格式和验证命令。
6. **主 Agent 集成**：复核公共边界，统一运行测试与构建。
7. **真实环境验证**：浏览器、生产和用户场景逐层验证。
8. **写入项目记忆**：记录决定、事故、结果和下一道门。
9. **重新回到用户**：报告证据、风险和一个明确的推荐下一步。

可以用一句口诀记住：

> 先对齐，再拆分；先样板，再扩展；先证据，再宣布；先验证，再增长。

## 八、对双方角色的总结

### 用户做对了什么

- 用非常直接的语言指出产品感受，而不是被已有实现绑架。
- 在关键阶段及时选择和授权，没有介入不必要的技术细节。
- 愿意让产品从开源项目目录转向全年龄新手作品，并以 K12 作为一条精细化学习路径。
- 在功能已经很多时，接受先做真实试教、暂缓账号与数据库的建议。

### AI 团队做对了什么

- 把简短意图持续翻译为结构化产品、工程契约和可验收任务。
- 通过目录所有权和公共 Schema 支持并行开发。
- 在抓取、内容、发布、密钥和未成年人数据上设置安全边界。
- 面对生产失败保留回滚和证据，逐层定位，而不是隐藏失败。
- 持续把对话结论写回仓库，让项目可以跨 Agent、跨会话接续。

## 九、最终判断

这次合作可以被称为一次成功的 Vibe Coding 实践，但成功的定义需要保持克制：

- **产品开发成功**：从想法形成了完整、上线、可维护的 OpenVibe。
- **协作机制成功**：人、主 Agent、子 Agent、测试和生产环境形成了清晰分工。
- **工程运行成功**：持续发现、人工审核、更新扫描、部署、回滚和监控已经跑通。
- **K12 专项效果尚待验证**：两场真实试教还没有完成，不能提前宣称分龄路线真正有效；全年龄路径后续也需要按不同生活阶段补充真实用户证据。

因此，下一步最有价值的动作不是继续无边界增加功能，而是并行做好两件小事：完成两场 4–8 人的 K12 真实试教；同时用少量大学生、职场人和银龄探索者核对全年龄入口是否让他们感到“这是为我准备的”。OpenVibe 的目标不是为每个年龄建立孤岛，而是让任何年龄的人都能从自己的问题出发，调用 AI、做出作品并成为作者。
